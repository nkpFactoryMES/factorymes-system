# Mock에서 실제 SMTP·Webhook 통신으로 넓힌 알림 흐름

기존 MES는 Inbox·Outbox·채널별원장과Mock공급자로알림흐름을검증했다. 다음에는‘성공을반환하는메서드’와‘다른서버가실제로받은메시지’를구분할필요가있었다. 개인포트폴리오의비용조건을지키기위해외부계정·키·실제수신자없이SMTP와HTTP를로컬서버로검증했다.

이메일은MailKit SMTP와Mailpit을선택했다. MIME·취소·SMTP상태를직접socket으로다시구현하지않고검증된라이브러리를사용하는편이업무로직에집중하기좋았다. 채팅은Slack Incoming Webhook형태의HTTP어댑터와별도로구현한수신기를선택했다. Slack무료플랜의앱/이력제한과Zulip/Rocket.Chat자체호스팅의운영책임을비교했으며,채팅제품전체를운영하는범위로늘리지않았다. 실제Slack발송을인증한검증이라고쓰지않는다.

관리자가선택한로컬시연도기존Inbox→Outbox→Delivery원장을지난다. 수신후영수증또는재시도를기록하되로컬capture를외부SENT로표시하지않는다. Worker는실제통신의실패를원장에남기고일시오류는3회까지만재시도한다. 영구오류와관리자수동재시도를분리하고식별자·입력해시·버전으로재전송을대조한다.

중복도한가지문제로묶지않았다. DB원장중복은행잠금·기수신감사로막고로컬HTTP수신기는같은ID와같은본문을기존기록으로받는다. 반면SMTP Message-ID는수신자중복억제보장이아니다. ACK를잃거나DBcommit이실패하면같은메일이중복수신될수있다. 이한계를기술선택의일부로기록했다.

검증도코드반환값과실제통신을나눴다. 공급자60/수신기74독립검사와실제SMTP·HTTP·Oracle61검사,새화면10검사,기존회귀129검사를합쳐334개를통과했다. Mailpit의디코딩메시지와다른프로세스의채팅기록을직접대조했고429/400/503·자동/수동재시도·화면표시까지확인했다.

과정에서메모리만먼저저장한저널이디스크실패뒤거짓ACK를만들수있음을보완했다. 여러조회사이에원장이커밋되면수신완료와옛횟수가섞이는화면경합도찾아표시와버튼의기준을같은원장스냅샷으로맞췄다. Claude는수신기·화면·브라우저와독립검토를맡았고GPT는Backend·공급자·계약·Compose·통합을나눴다.

최종13서비스는정상이며Oracle계정·업무이력·볼륨은보존했다. 유료API나실제외부발송은없다. 상세선택근거·실패수정·한계·재현명령·증거는[email-chat-adapters-decision.md](email-chat-adapters-decision.md)에남겼다. 실제외부목적지·TLS/OAuth·반송·수신자설정은다음검토범위다.
