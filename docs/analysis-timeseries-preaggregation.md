# AI 시계열 사전 집계 설계·구현 (2026-11-16)

## 해결하는 문제
기존 입력 생성은 원시 숫자 관측을 애플리케이션에 읽고 10,000건을 넘으면 거절했다.
1초 간격의 하루 수집은 설비 하나만 86,400표본이므로 예약 Mock 분석도 실패했다.
Oracle에서 요청 기간의 전체 GOOD 숫자 자료를 먼저 집계하고, 지표별 요약만 Backend로 전송한다.
기존 AnalysisSnapshot에 결과를 고정한 뒤 같은 Gateway·AI Connector·Mock Provider 경로로 보낸다.

## 비교와 선택
- 원본 일부만 자르거나 샘플링하면 극값·평균·마지막 값이 변할 수 있어 선택하지 않았다.
- 영속 분 단위 집계 테이블은 반복 조회에 유리하지만 지연 도착, 재집계, 원본 정정,
  집계 진행 위치와 부분 완료를 관리해야 한다. 이번 단일 개발·현재 데이터량에는 추가하지 않았다.
- 요청 시 Oracle CTE로 분별 집계 후 지표별 합산하는 방식을 선택했다. 새 DDL과 API 변경이 없다.
  DB는 여전히 해당 기간 원본을 처리한다. DB 계산량이 상수이거나 대규모 운영 성능이 보장된다는 뜻은 아니다.
- 이후 실제 부하 측정으로 반복 조회 비용이 확인되면 영속 rollup과 watermark를 별도 설계한다.

## 계산 규격
기간은 UTC [시작, 종료), 1분 이상 24시간 이하이며 TIMESTAMP(6) 정밀도를 유지한다.
분 버킷은 시작 시각 기준 FLOOR(경과 시간/60초)다. 날짜 변환으로 소수초를 버리지 않는다.
GOOD이며 NUMERIC_VALUE가 있는 값만 사용한다. BAD·UNCERTAIN·문자 상태 값은 제외한다.
지표 코드와 단위를 함께 그룹화하며 NULL 단위와 명시 단위가 혼재하면 거절한다.
각 분의 건수·합계·최소·최대·마지막 값을 만든 뒤 기간 전체로 합친다.
평균은 SUM(분별 합계)/SUM(분별 건수)이며 분별 평균의 단순 평균을 쓰지 않는다.
Oracle ROUND(...,6) 후 NUMBER(18,6)으로 읽어 소수 표현과 해시를 안정화한다.
마지막 값은 OCCURRED_AT_UTC, TELEMETRY_ID 순서로 결정한다.
표본 수는 여러 지표가 같은 이벤트를 사용해도 DISTINCT TELEMETRY_ID로 한 번 센다.
관측 비율은 지표 전체의 서로 다른 분 버킷 수/CEIL(기간 분 수)다. 가동률이나 예측 신뢰도가 아니다.
지표·단위 그룹 최대 50개, 확인용 51행까지만 전송한다. 원시 10,000행 상한은 제거했다.
중지 이력의 기존 10,000행 보호와 최소 표본·관측 비율 부족 판정은 유지한다.

## 구현과 경계
AnalysisService.Aggregation.cs의 단일 SQL이 관측→버킷→분별→기간별→전체 표본/관측 비율을 계산한다.
QueueCore가 소유한 Oracle 연결·트랜잭션을 사용하고 SQL 제한 시간은 30초다.
Input.cs는 요약 결과와 기존 중지 시간 합집합·경보 수를 조합한다.
기존 불변 스냅숏·설정 해시·요청 UUID 멱등·Service JWT·Cookie/CSRF는 그대로 적용된다.
기존 실패 작업과 스냅숏은 다시 쓰지 않는다. 화면은 과거 ANALYSIS_INPUT_LIMIT의 의미도 설명한다.
예약은 기존 Quartz의 전날 24시간 고정 창과 동일 요청 ID를 사용한다.
대상 선택 1개·최대 20설비·dispatch deadline 등 기존 제한은 이번에 확대하지 않는다.

## 담당과 검증 방법
GPT: Backend SQL/Input, Tooling 대용량·회귀 시험, 공통 빌드·배포·기록.
Claude: Analyses 화면 안내와 브라우저 회귀, Backend 읽기 독립 검토.
대용량 시험은 실제 Oracle에 격리된 비활성 수집 대상을 만들고 86,400이벤트·172,800숫자 행을 넣는다.
이는 집계·API·예약·Gateway·Connector 통합 검증이며 실제 PLC 수집 처리량 시험은 아니다.
수동/예약 성공, 동일 입력 해시, 가중 평균, 소수초 경계, 품질 제외, 단위 혼재 거절,
마지막 값 동률, 예약 중복 방지, Mock UNKNOWN/채택 안 함·경보 미생성을 확인한다.
최종 실행 결과와 시간은 아래 완료 기록에 추가한다. 실제 모델·유료 호출·이메일/채팅 실발송은 없다.

## 독립 검토와 이번에 남긴 한계
Claude가 SQL·입력 조합·대용량 fixture를 읽기 전용으로 검토했고 계산 결함은 발견하지 않았다.
예약 대상은 기존 정책대로 ID 순 최대 20개여서 대상이 많으면 새 설비가 제외될 수 있다.
이번 fixture는 실제 예약 성공을 확인했지만 반복 시험 DB에서 대상 수가 늘면 선택 범위를 먼저 확인해야 한다.
공정한 대상 순환은 집계 정확도와 별개의 후속 설계다.
집계는 기존 요청 처리의 gate·대상/사용자 잠금 트랜잭션 안에서 수행된다.
현재 멱등·스냅숏 저장 경계를 보존했으며 고부하에서는 잠금 대기 측정과 경계 분리가 필요하다.
이때 잠금 밖 집계와 재검사 사이 데이터 변화를 함께 설계해야 하므로 이번에 임의로 분리하지 않았다.

## 실제 Oracle 결과
대용량 전용 시험 25항목과 기존 AI API 58항목이 통과했다.
86,400이벤트·172,800숫자 행 생성은 25,578ms, 수동 입력 접수·스냅숏 확인은 847ms였다.
847ms는 SQL 단독 시간이 아니라 HTTP·스냅숏 조회를 포함한 한 번의 로컬 측정이다.
메모리 사용량이나 운영 환경 처리량의 벤치마크로 해석하지 않는다.
온도 min/max/mean/last=0/99/49.5/99, 두 번째 지표=1/86400/43200.5/86400을 확인했다.
예약 결과는 SUCCEEDED, UNKNOWN·MockFlag=true·Accepted=false다.
기존 10,001건 집중 관측 fixture는 이제 거절되지 않고 관측 비율 부족 상태로 기록된다.
원시 자료가 많다는 이유로 실패하는 것과 자료의 시간적 분포가 부족한 것을 구분한다.
원본 증빙: verification-results/analysis-aggregation-verification.json, analyses-verification.json.
